Для решения задачи оптимального планирования производства в кластере, описанной в файле `ClusterProblem.md`, необходимо формализовать задачу как задачу **математического программирования** (чаще всего линейного или смешанного целочисленного).

Исходя из предоставленной структуры базы данных, мы имеем дело с моделью «затраты-выпуск» (input-output model) на уровне предприятий.

Ниже представлены варианты формирования целевых функций и ограничений для **отдельного участника** (производителя), а также анализ недостающих данных.

### 2. Варианты целевых функций (Objective Function)

Целевая функция определяет, к чему стремится конкретный производитель, «перетягивая одеяло» на себя.

#### Вариант А: Максимизация маржинальной прибыли (Экономический подход)
Это наиболее реалистичный сценарий для независимого агента. Производитель хочет максимизировать разницу между выручкой от продаж и затратами на производство.

$$Max \ Z = \sum_{j \in P_{own}} (Price_j \cdot x_j) - \sum_{i \in Res} (Cost_i \cdot r_i) - (FixedCosts)$$

* $x_j$: объем произведенной продукции $j$.
* $r_i$: объем потребленных ресурсов $i$.
* **Проблема:** В текущей БД нет цен (`Price`) и стоимости закупки ресурсов (`Cost`).
* **Рекомендация:** Добавить таблицы цен реализации и стоимости сырья.

#### Вариант Б: Минимизация отклонений от внешнего плана (Исполнительский подход)
Если предприятие жестко ориентировано на выполнение заказа кластера, его цель — произвести ровно столько, сколько просит план, или больше, но с минимизацией штрафов за недопоставку.

$$Min \ Z = \sum_{j} (w_j \cdot |x_j^{sales} - Plan_j|)$$

* [cite_start]$Plan_j$: значение из таблицы `plan_value`[cite: 5].
* $x_j^{sales}$: объем продукции, отгруженной внешнему заказчику.
* $w_j$: штрафной коэффициент (важность выполнения плана по продукту).

#### Вариант В: Максимизация загрузки мощностей (Технократический подход)
Цель — максимизировать валовый выпуск, чтобы избежать простоя оборудования/персонала, игнорируя эффективность.

$$Max \ Z = \sum_{j \in P_{own}} (k_j \cdot x_j)$$

* $k_j$: коэффициент трудоемкости (нормо-часы) для продукта $j$.

### 3. Способы задания ограничений (Constraints)

Ограничения определяют область допустимых решений.

#### 3.1. Технологические ограничения (Баланс материалов)
Основываются на таблице `cost`. Нельзя произвести продукт, не затратив ресурсы.
Для каждого продукта $j$, производимого предприятием:

$$\text{Потребность в ресурсе } i = \sum_{j} (Coefficient_{ij} \cdot x_j)$$

[cite_start]Где $Coefficient_{ij}$ берется из колонки `coefficient` таблицы `cost`[cite: 1, 20].
[cite_start]*Пример из данных:* Для производства продукта `MB` (id=6) нужен ресурс `SU-A` (id=5) с коэффициентом 3[cite: 20]. Значит, $Need_{5} = 3 \cdot x_{6}$.

#### 3.2. Ограничения по производственным мощностям (Capacity)
Каждый производитель имеет лимит (станко-часы, человеко-часы, площадь).
**В базе данных это отсутствует.**
*Предложение:* Создать ограничение вида:
$$\sum_{j} (Time_j \cdot x_j) \le TotalAvailableTime$$
Где $Time_j$ — время на единицу продукции.

#### 3.3. Ограничения по доступности сырья (Supply Chain)
Если производитель C3 зависит от поставки сырья от производителя C1, то план C3 ограничен выпуском C1.
$$r_i^{purchased} \le SupplyLimit_i$$
Это и есть точка конфликта: $SupplyLimit_i$ зависит от плана другого участника.

#### 3.4. Условие неотрицательности
$$x_j \ge 0$$

### 4. Формализация модели для отдельного участника

Для расчета оптимального плана конкретного `producer_id` предлагается следующая структура задачи линейного программирования (LP):

**Дано:**
1.  [cite_start]$O$: Множество продуктов, производимых текущим агентом (`products` где `producer_id = X`)[cite: 12].
2.  [cite_start]$I$: Множество потребляемых ресурсов (из `cost`)[cite: 1].
3.  [cite_start]$A_{ij}$: Коэффициенты расхода (`cost.coefficient`)[cite: 1].
4.  [cite_start]$D_j$: Внешний спрос (`plan_value.value`)[cite: 3].

**Переменные:**
* $x_j$: Объем производства собственного продукта $j$.
* $y_j$: Объем продажи продукта $j$ внешнему заказчику.
* $z_{ij}$: Объем использования своего продукта $i$ для производства продукта $j$ (внутреннее потребление).

**Задача (пример смешанной стратегии):**
Максимизировать Прибыль (если есть цены) ПРИ УСЛОВИИ выполнения плана не менее чем на 80%.

**Система ограничений:**

1.  **Баланс производства и распределения:**
    Все, что произвели ($x_i$), уходит либо на продажу ($y_i$), либо на внутреннюю переработку для других продуктов.
    $$x_i = y_i + \sum_{k \in O} (A_{ik} \cdot x_k)$$
    *(Здесь $A_{ik}$ показывает, сколько продукта $i$ нужно для выпуска продукта $k$. Это рекурсивная зависимость внутри завода)*.

2.  **Ограничение внешнего спроса (или плана):**
    $$y_i \le D_i \text{ (не производить на склад больше спроса)}$$
    ИЛИ
    $$y_i \ge D_i \text{ (обязательство выполнить план)}$$

3.  **Ресурсные ограничения (Вход):**
    Для закупаемых ресурсов (где $producer\_id \neq X$):
    $$\sum_{j \in O} (A_{rj} \cdot x_j) \le \text{Доступный лимит закупки ресурса } r$$

### 5. Резюме и недостающие данные

Для полноценного расчета **необходимо дополнить схему данных**:

1.  **Таблица цен (`prices`):** Цена продажи продукта и цена закупки ресурса. Без этого нельзя посчитать «максимизацию прибыли».
2.  **Таблица мощностей (`capacity`):** Ограничения на ресурсы самого производителя (фонд рабочего времени, макс. производительность оборудования). Без этого план будет стремиться к бесконечности.
3.  **Таблица запасов (`inventory`):** Текущие остатки на складах (хотя в задаче пока сказано игнорировать, для старта производства часто нужны начальные остатки).



Это классическая проблема **декомпозиции** в исследовании операций. Когда вы говорите, что "общая система уравнений сложна", вы правы: решать глобальную задачу для всего кластера сразу (централизованно) часто невозможно из-за коммерческой тайны участников (никто не хочет раскрывать свои точные формулы затрат) или вычислительной сложности.

Поскольку вы хотите использовать **Посредника** (Mediator) и итеративный подход ("подгонку"), наиболее подходящим математическим фундаментом здесь являются методы **декомпозиции Данцига-Вульфа** или **Лагранжева релаксация**, но переложенные на язык "переговоров".

Вот 3 варианта алгоритма работы Посредника, от рыночного до директивного.

---

### Вариант 1: Метод "Теневых цен" (Рыночный аукцион)
*Подходит, если участники чувствительны к цене, а Посредник имеет бюджет для стимулирования.*

В этом подходе Посредник не диктует *сколько* производить (количество), а меняет *внутренние цены* (трансфертные цены) на продукты внутри кластера, пока спрос и предложение не сойдутся.

**Алгоритм:**
1.  **Инициализация:** Посредник объявляет начальные цены на все промежуточные продукты (например, себестоимость + 10%).
2.  **Шаг производителей:** Каждый завод $k$, видя эти цены, решает свою локальную задачу максимизации прибыли:
    $$Max \ Profit_k = (Prices_{out} \cdot Output) - (Prices_{in} \cdot Input) - Costs$$
    Они отправляют Посреднику свои планы: "При таких ценах я куплю 50 ед. сырья и произведу 100 ед. товара".
3.  **Шаг Посредника (Сверка):** Посредник суммирует все планы и сравнивает с Генеральным планом.
    * Если продукта $X$ произведено меньше, чем нужно Генеральному плану -> Посредник **повышает** внутреннюю закупочную цену на $X$.
    * Если продукта $Y$ (сырья) требуется больше, чем могут поставить поставщики -> Посредник **повышает** цену на сырье $Y$, чтобы поставщику стало выгодно производить его больше (даже с учетом овертаймов), а потребитель начал его экономить.
4.  **Итерация:** Новые цены рассылаются участникам. Цикл повторяется, пока разрывы не станут минимальными.

> **Роль LLM:** LLM здесь выступает как аналитик, который объясняет изменение цены: *"Уважаемый C3, мы подняли закупочную цену на SU-A на 5%, так как C4 критически не хватает вашего ресурса для закрытия внешнего контракта."*

---

### Вариант 2: Метод "Штрафов за отклонение" (ADMM - Alternating Direction Method of Multipliers)
*Подходит, если Генеральный план жесткий, и его нужно выполнить любой ценой.*

Здесь Посредник спускает каждому заводу персональный план-ориентир. Завод может отклониться от него, но за каждое отклонение налагается "виртуальный штраф", который снижает его расчетную прибыль (или рейтинг в кластере).

**Алгоритм:**
1.  **Декомпозиция:** Посредник берет Генеральный план и "разбивает" его на квоты для участников (первичное приближение).
2.  **Локальная оптимизация:** Завод считает: "Чтобы выполнить этот план, мне нужно работать в 3 смены, это убыточно. Я лучше заплачу небольшой штраф, но произведу меньше". Завод выдает свой *оптимальный* (для себя) план, который отличается от спущенного.
3.  **Обновление штрафов:** Посредник видит "бунт" (отклонение).
    * Он увеличивает "цену штрафа" (коэффициент $\lambda$) именно для этого дефицитного товара.
    * Он обновляет план-ориентир, усредняя желания всех участников.
4.  **Итерация:** В следующем раунде заводу становится *слишком дорого* отклоняться, и он вынужден искать резервы (например, нанимать людей), чтобы приблизиться к плану.

$$TargetFunc_{new} = (RealProfit) - \lambda \cdot (MyOutput - SuggestedPlan)^2$$

---

### Вариант 3: "Умный переговорщик" (Агентный подход с LLM)
*Наиболее реалистичный для бизнес-среды.*

Это гибридный подход. Посредник (LLM) анализирует не только числа, но и *ограничения* ("почему вы не можете?").

**Логика работы Посредника:**

1.  **Сбор данных:** Все участники загружают свои идеальные планы и, что важно, **список своих "узких мест"** (bottlenecks) — например: "не хватает людей", "нет сырья", "дорогое электричество".
2.  **Выявление конфликта:** Посредник видит разрыв: *Ген. план требует 1000 ед. PC-A, а Производитель C1 дает только 800.*
3.  **Анализ причин (Chain of Thought):**
    * [cite_start]Посредник смотрит в базу: C1 делает PC-A[cite: 45].
    * Для PC-A нужны ресурсы от C2, C3, C5 (исходя из зависимостей в `cost` или логики продукта).
    * Посредник спрашивает C1: "Почему 800? Проблема в мощностях или в поставках?"
4.  **Генерация компромисса:**
    * Если C1 отвечает "C3 не отгружает мне MB (Motherboards)", Посредник идет к C3.
    * Посредник предлагает сделку: *"C3, если вы увеличите выпуск MB на 200 ед., мы разрешим вам снизить план по другому (менее приоритетному) продукту"* ИЛИ *"Кластер компенсирует вам затраты на срочность"*.

Ниже представлен псевдокод алгоритма работы **Интеллектуального Посредника (Mediator Agent)**.

Этот алгоритм реализует итеративный процесс ("переговоры"), где LLM управляет параметрами для решателя (Solver), анализирует результаты и корректирует входные данные (цены или штрафы), чтобы свести планы участников к единому Генеральному плану.

### Архитектура решения

1.  **LLM (Orchestrator):** Мозг системы. Формирует контекст, вызывает инструменты, интерпретирует результаты (почему план не сошелся?) и принимает решение об изменении параметров.
2.  **Tools (Инструменты):**
      * `DB_Tool`: Чтение структуры продукта и текущих планов из PostgreSQL (таблицы `cost`, `plan_value` и т.д.).
      * `Solver_RPC`: Внешний сервис (например, на базе Gurobi, CPLEX или Google OR-Tools), который решает задачу линейного программирования (LP) для конкретного завода.

### Псевдокод (Python-style)

```python
class ClusterMediator:
    def __init__(self):
        self.iteration_limit = 10
        self.convergence_threshold = 0.05 # 5% допустимое отклонение
        # Начальные "теневые цены" или штрафы за невыполнение плана
        self.incentives = {} 

    def run_negotiation_session(self, plan_id):
        """
        Главный цикл согласования планов.
        """
        print(f"Начинаем согласование для плана {plan_id}")

        # 1. Получение Генерального плана (Внешний спрос)
        # [cite_start]Читаем из tables: plan_value [cite: 4][cite_start], ext_consumer_plan [cite: 3]
        target_demand = tools.db_query(f"""
            SELECT p.code, pv.value 
            FROM plan_value pv 
            JOIN products p ON pv.id_product = p.id
            WHERE pv.id_extconsumerplan = '{plan_id}'
        """)

        for i in range(self.iteration_limit):
            print(f"--- Итерация {i+1} ---")
            
            # 2. Сбор предложений от каждого участника (Локальная оптимизация)
            cluster_proposals = {}
            [cite_start]producers = tools.db_query("SELECT id, code FROM producers") [cite: 8]

            for producer in producers:
                # LLM вызывает решатель для каждого завода отдельно
                # Завод пытается максимизировать СВОЮ прибыль с учетом текущих цен/штрафов
                proposal = self.optimize_producer_plan(producer, target_demand)
                cluster_proposals[producer['code']] = proposal

            # 3. Агрегация результатов (Supply Chain Calculation)
            # Проверяем, хватает ли промежуточных продуктов (например, MB для PC-A)
            # [cite_start]Используем таблицу cost [cite: 1] для связей
            global_balance = self.calculate_global_balance(cluster_proposals, target_demand)

            # 4. Проверка сходимости
            if self.is_converged(global_balance):
                return self.finalize_plan(cluster_proposals)
            
            # 5. Анализ конфликтов и корректировка (LLM Reasoner)
            adjustments = self.llm_resolve_conflicts(global_balance, cluster_proposals)
            
            # Применяем новые цены/штрафы для следующего круга
            self.incentives.update(adjustments)

        return "Не удалось найти консенсус. Требуется вмешательство человека."

    def optimize_producer_plan(self, producer, target_demand):
        """
        Формирует задачу для Solver RPC.
        Моделирует поведение "эгоистичного" агента.
        """
        # [cite_start]Сбор данных о технологии завода из таблицы cost [cite: 1]
        # BOM: Что завод производит и что потребляет
        tech_map = tools.db_query(f"""
            SELECT r.code as resource, res.code as product, c.coefficient
            FROM cost c
            JOIN products r ON c.id_product_resource = r.id
            JOIN products res ON c.id_product_result = res.id
            WHERE res.producer_id = {producer['id']}
        """)

        # Формирование JSON для Solver RPC
        # Целевая функция: Maximize (Sales * Price - Costs - Penalties)
        solver_payload = {
            "objective": "maximize_profit",
            "constraints": [
                # Технологические ограничения (ресурс = коэф * продукт)
                {"type": "bom_balance", "data": tech_map},
                # Ограничение по внешнему спросу (из target_demand)
                # Если incentives высокие, завод захочет выполнить план
                {"type": "soft_target", "targets": target_demand, "penalties": self.incentives}
            ],
            "parameters": {
                # Цены берутся из self.incentives (динамические) или базовых прайсов
```

### Пояснения к ключевым блокам

1.  **`optimize_producer_plan`**: Здесь происходит магия декомпозиции. Мы не решаем гигантское уравнение для всего кластера. [cite\_start]Мы просим RPC-сервер решить маленькую задачу для завода C1 (`producer_id=1` [cite: 39]).

      * [cite\_start]Если C1 видит, что штраф за невыполнение плана по `PC-A` [cite: 45] выше, чем затраты на производство, RPC-солвер выдаст решение "Производить".
      * Если затраты слишком высоки, он выдаст "Произвести меньше и заплатить штраф".

2.  **`llm_resolve_conflicts`**: Это замена сложным математическим алгоритмам обновления лагранжевых множителей.

      * [cite\_start]Вместо слепого градиентного спуска, LLM читает контекст: *"Ага, C3 [cite: 42] является бутылочным горлышком для C1. Но C3 жалуется на низкую маржинальность. Давайте поднимем виртуальную закупочную цену на `MB` для внутренних расчетов"*.
      * Это меняет `self.incentives`, и на следующей итерации Solver для C3 увидит: "Ого, за `MB` теперь платят больше\! Выгодно ввести вторую смену".
